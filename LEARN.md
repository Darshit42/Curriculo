# Learn Curriculo

> A guided course through `github.com/Darshit42/Curriculo`: 8 lessons, ordered from entry points to the parts that trip people up, each tied to real files and followed by a short quiz.
> Generated by [Curriculo](https://github.com/Darshit42/Curriculo) on 2026-11-08. Take it interactively with `npx github:Darshit42/Curriculo learn`.

## Orientation

Curriculo is a dependency-free Node.js tool that turns any Git repository into a guided, interactive course: it ingests source files, ranks and slices them into teaching material, synthesizes lessons via the BharatCode API or offline heuristics, and emits a `.curriculo/course.json` manifest plus a commit-friendly `LEARN.md`. The code splits into two layers: `engine/` is a UI-less library exposing the whole pipeline, and `cli/` is a thin command-line shell (with an interactive TUI) built on top of it. Execution starts at `cli/index.js`, which parses args and calls `generateCourse` / `writeOutputs` from the engine entry point `engine/index.js`. Read the CLI first to see how the commands are wired, then `engine/index.js` for the ingest -> rank -> synthesize -> manifest -> render flow, and from there dive into whichever stage you need.

## 1. CLI entry and command wiring

**Files:** [`cli/index.js`](cli/index.js)

`cli/index.js` is the single entry point for the entire tool. It is a shebang'd ES module (line 1) that does three things: parses command-line arguments, dispatches to a command handler, and formats output. It contains no business logic — every substantive operation is delegated to the engine.

### Imports and the engine boundary

Lines 6–16 import the engine's public surface from `../engine/index.js`: `generateCourse`, `ingest`, `rankFiles`, `resolveSource`, `loadCourse`, `writeOutputs`, `manifestPath`, `badgeMarkdown`, and `DEFAULTS`. Two more helpers come from `../engine/util.js` (line 17), and the TUI lives in `./tui.js` (line 18). This import list is effectively the engine's API contract — if you want to know what the engine exposes, this is the quickest map.

### Argument parsing and dispatch

`main()` at line 171 uses Node's built-in `parseArgs` (from `node:util`, line 4) with `allowPositionals: true`. The first positional is the subcommand; the rest are passed through as `args`. Numeric options like `--lessons` and `--top` are declared as `type: 'string'` (lines 178–181) and validated later by the `int()` helper at line 64, which calls `fail()` if the value isn't a positive integer. The switch at line 196 routes to five handlers:

| Command | Handler | What it calls in the engine |
|---------|---------|-----------------------------|
| `gen` / `generate` | `cmdGen` (line 81) | `generateCourse` |
| `learn` | `cmdLearn` (line 127) | `loadCourse`, then `runTUI` or `printCourse` |
| `render` | `cmdRender` (line 143) | `loadCourse` + `writeOutputs` |
| `rank` | `cmdRank` (line 156) | `resolveSource` + `ingest` + `rankFiles` |
| `badge` | inline (line 207) | `badgeMarkdown` |

### Course root resolution

`findCourseRoot(start)` at line 71 walks **up** the directory tree from the given path, checking each level for a file at `manifestPath(dir)`. This means `curriculo learn` works from any subdirectory of a repo that already has a `.curriculo/course.json`. If no manifest is found, it returns `null` and the caller prints an error.

### The `--learn` chain

A subtle wiring detail: `cmdGen` at line 124 checks `opts.learn` and, if true, immediately calls `cmdLearn([result.root])`. So `curriculo gen . --learn` generates the course and then drops you into the TUI in one invocation, without a second command.

**Watch out:** `findCourseRoot` uses `manifestPath(dir)` (imported from the engine) to detect a course directory, but it does *not* validate that the manifest is well-formed. A corrupt or partial `course.json` will pass the existence check and only fail later inside `loadCourse`, producing a less obvious error message than "No course found."

## 2. Engine pipeline orchestration

**Files:** [`engine/index.js`](engine/index.js)

`engine/index.js` is the whole pipeline in one screen: the file-level comment at the top states the order — ingest → rank → synthesize → manifest → LEARN.md — and the body of `generateCourse()` (line 39) executes exactly that sequence.

**The exported surface.** Lines 15–21 are re-exports that define what the CLI and anything else may depend on: `ingest`/`resolveSource` from `./ingest.js`, `rankFiles`/`selectTeachingSet` from `./rank.js`, slicing helpers from `./slice.js`, the model client from `./llm.js`, everything from `./manifest.js` via `export *`, plus `renderLearnMd`, `offlineCourse`, and `badgeMarkdown`. Line 23 fixes the defaults that govern a run: `DEFAULTS = { maxLessons: 8, top: 24, budget: 250_000, concurrency: 8 }`. If a CLI flag isn't passed, one of these four numbers decides the behavior.

**The pipeline.** `generateCourse()` first decides model vs. offline (lines 54–66): unless `offline` is set, it calls `configFromEnv(env)` and `missingConfig(cfg)`, throwing an `NO_CONFIG` error listing exactly which variables are absent. Then it resolves the source (`resolveSource`, line 68), ingests files (`ingest`, line 70 — throwing if none are readable), ranks them (`rankFiles`, line 72), and trims to the teaching set (`selectTeachingSet(ranked, { top })`, line 73).

Synthesis forks at line 77: `offlineCourse({ ing, ranked, teaching, maxLessons })` for heuristics, or a real `BharatCodeClient` constructed with a cache dir under `<root>/<STATE_DIR>/cache`, the token `budget`, `useCache`, and a swappable `fetchImpl` (lines 80–86), feeding `synthesizeWithModel` (line 87). Lesson 6 covers that client; lesson 7 covers the fork.

**Stats, validation, output.** Lines 90–98 assemble `stats` — file counts, duration, token usage (zeroed when offline), and `degradedLessons`. `buildCourse` (line 99) assembles the manifest object, `validateCourse` (line 100) checks every referenced path against the ingested file set, and any failure throws before anything is written. Finally `writeOutputs(root, course)` (line 26) saves the manifest, renders `LEARN.md` via `renderLearnMd`, and drops a `.gitignore` into the state dir so `cache/`, `progress.json`, and `context.json` never reach a commit.

Read the file top-down: imports → re-exports → `DEFAULTS` → `writeOutputs` → `generateCourse`.

**Watch out:** in the online path, `client` is first a bare `{ cfg }` holder (line 65) and only becomes a real `BharatCodeClient` at line 80 — so if you reorder those blocks, `client.cfg` will be undefined.

## 3. Shared utilities

**Files:** [`engine/util.js`](engine/util.js)

`engine/util.js` is the only module in the repo that imports exclusively from Node built-ins (`node:crypto`, `node:fs`, `node:path`). Every other file in `engine/` and `cli/` can depend on it, but it depends on nothing else in the project. That makes it the safest place to start when you need to understand a helper without pulling in pipeline context.

### What's inside

The file exports thirteen small functions, each solving one narrow problem:

| Function | Line | Purpose |
|----------|------|---------|
| `sha()` | 6 | SHA-256 hex digest; used to fingerprint file content so the ingest stage can skip unchanged files. |
| `estTokens()` | 11 | Rough token count (~4 chars/token) for budgeting before a model call. |
| `pool()` | 16 | Concurrency-limited async map that preserves input order. The synthesis stage uses it to fan out multiple API calls without exceeding a rate limit. |
| `readJSON()` / `writeJSON()` | 30 / 38 | Safe JSON I/O. `writeJSON` creates parent directories; `readJSON` returns a fallback on any error. These are the workhorses behind the `.curriculo/course.json` manifest. |
| `toPosix()` | 43 | Normalizes path separators to `/` so the manifest is identical on Windows and POSIX. |
| `slugify()` | 47 | Converts arbitrary strings to URL-safe slugs (max 40 chars). Used for lesson IDs and output filenames. |
| `seededRandom()` / `shuffle()` | 57 / 69 | Deterministic PRNG (mulberry32) and Fisher-Yates shuffle. The ranking stage uses these so that the same input always produces the same lesson order. |
| `parseJSONLoose()` | 80 | Extracts the first JSON object from raw model text, tolerating markdown fences and surrounding prose. Critical for the model synthesis path. |
| `formatDuration()` | 102 | Human-readable elapsed time for CLI progress output. |
| `fileExt()` / `fileStem()` | 109 / 115 | Split a path into extension and stem. The ingest stage uses `fileExt` to classify files by language. |

### How to read it

Top to bottom is fine — there are no internal dependencies between the functions except `shuffle` calling `seededRandom`, which calls `sha`. If you want to see a function in action, jump to the stage that uses it: `pool` and `parseJSONLoose` appear in the synthesis path (lesson 7), `readJSON`/`writeJSON` in the manifest stage (lesson 4), and `sha` in ingest (lesson 5).

**Watch out:** `readJSON` at `engine/util.js:30` catches *all* exceptions, not just `JSON.parse` failures. A permission error, a missing file, or a disk error all silently return the fallback value. If you add a new call site and the file is unexpectedly absent, you'll get `null` with no warning — check the return value explicitly rather than assuming the file exists.

## 4. Manifest as source of truth

**Files:** [`engine/manifest.js`](engine/manifest.js) · [`engine/render.js`](engine/render.js)

### What the manifest is and where it lives

`engine/manifest.js` is the single source of truth for all course data. It defines the on-disk layout, the validation rules, and the canonical shape of the course object that every other stage reads or writes.

Two constants anchor the file: `MANIFEST_VERSION = 1` (line 4) and `STATE_DIR = '.curriculo'` (line 5). All state files live under `.curriculo/` in the target repo. `manifestPath(root)` (line 7) resolves to `.curriculo/course.json`; `progressPath(root)` (line 11) resolves to `.curriculo/progress.json`. The latter is consumed by the TUI (lesson 8) to track which lessons a learner has completed.

### Building and validating

`buildCourse()` (line 82) assembles the manifest in a fixed field order: `version`, `repo`, `generatedAt`, `model`, `summary`, `lessons`, and optionally `stats`. Each lesson gets an `id` generated by `lessonId()` (line 77), which produces a zero-padded, slugified string like `01-cli-entry-and-command-wiring`. The `degraded` flag is only included when explicitly `true` (line 96), keeping the JSON clean for the common case.

Validation is layered. `quizError()` (line 19) checks a single question's shape. `lessonErrors()` (line 40) checks a lesson's title, files, body, and quiz array, and—when a `knownFiles` set is provided—verifies every referenced file actually exists in the repo. `validateCourse()` (line 57) orchestrates both, also enforcing unique lesson IDs and required top-level fields.

`loadCourse(root)` (line 102) reads the JSON from disk and calls `validateCourse` without a `knownFiles` set. If validation fails it throws an `Error` whose `.errors` property carries the full list. `saveCourse(root, course)` (line 114) is a thin wrapper around `writeJSON`.

### Rendering to LEARN.md

`engine/render.js` is a pure presentation layer. `renderLearnMd(course)` (line 13) takes a validated course object and returns a single Markdown string. It emits an orientation section from `course.summary`, a course map with anchor links, then each lesson with its file links, body, and a collapsible quiz block using `<details>` elements. File paths are turned into relative Markdown links via `fileLink()` (line 5), which URL-encodes each path segment.

`badgeMarkdown()` (line 73) returns a Shields.io badge string a maintainer can paste into their README.

### How it connects

The engine pipeline (lesson 2) calls `buildCourse` after synthesis, then `saveCourse` to persist. The CLI's `learn` command (lesson 1) calls `loadCourse` to hydrate the TUI. `renderLearnMd` is called by the CLI's `gen` command to produce the `LEARN.md` file that gets committed alongside the repo.

**Watch out:** `loadCourse` does not pass `knownFiles` to `validateCourse`, so a stale manifest that references files deleted in a later commit will load without error. File-existence checks only happen during generation, not at load time.

## 5. Ingesting and selecting files

**Files:** [`engine/ingest.js`](engine/ingest.js) · [`engine/rank.js`](engine/rank.js) · [`engine/slice.js`](engine/slice.js)

### The three stages: candidate discovery, ranking, slicing

Read the three files in this order — `engine/ingest.js`, then `engine/rank.js`, then `engine/slice.js` — because each hands its output to the next: a list of candidate files, then a ranked/pruned teaching set, then per-file signal slices that keep prompts within budget.

**Ingesting.** `engine/ingest.js` decides what a file even is. `resolveSource()` (`engine/ingest.js:106`) handles both shapes of input: `isRemote()` (`:66`) detects `https://`, `git@`, `ssh://`, and `git://` URLs, and remotes are normalized by `normalizeRemote()` (`:75`) and cloned into a home directory (`reposHome()`, `:96`, honoring `CURRICULO_HOME`). Locally, `ingest()` (`:190`) lists files with `gitListFiles()` (`:146`) and falls back to `walkFiles()` (`:157`). Filtering is layered: `IGNORE_DIRS` (`:8`) and `shouldSkip()` (`:53`) drop build/vendored directories, `BINARY_EXT` (`:15`) plus `looksBinary()` (`:180`) drop non-text, `LOCK_FILES` (`:23`) drop lockfiles, and — critically — `isSecretPath()` (`:48`) blocks `SECRET_PATTERNS` (`:30`) so credential-like paths are never read or sent to a model. Two hard caps govern volume: `MAX_FILE_BYTES = 300 * 1024` and `MAX_FILES = 6000` (`:45–46`).

**Ranking.** `engine/rank.js` turns that candidate list into teaching order. `CODE_EXT` (`engine/rank.js:5`) separates source from config/docs; `ENTRY_NAMES` (`:12`) and `declaredEntries()` (`:23`) surface package-declared entry points; `TEST_RE` (`:18`), `PERIPHERAL_RE` (`:19`), and `CORE_DIR_RE` (`:20`) classify tests, examples, and core directories. `computeFanIn()` (`:159`) counts importers as a centrality signal. `rankFiles()` (`:218`) composes these into a score, and `selectTeachingSet()` (`:267`) prunes to `top = 24` files with at most `maxPeripheral = 2` — this is the teaching set that reaches the manifest described in lesson 4.

**Slicing.** `engine/slice.js` works per selected file. `extractSymbols()` (`engine/slice.js:43`) applies `DECL_PATTERNS` (`:6`) — regexes for JS/TS, Python, Go, Rust, Java/Kotlin and more — to find declarations. `leadingDoc()` (`:103`) captures the doc comment via `commentAt()` (`:68`), and `signalSlice()` (`:129`) assembles the top of file plus declarations, capped at `maxChars = 3000` and `headLines = 30`, so synthesis prompts stay small.

**Watch out:** `gitListFiles()` only sees tracked files — in a non-Git directory the `walkFiles()` fallback runs instead, so untracked-but-present files can silently change the candidate set depending on whether the repo has a `.git`.

## 6. Model client and prompts

**Files:** [`engine/llm.js`](engine/llm.js) · [`engine/prompts.js`](engine/prompts.js)

### What these two files do

`engine/llm.js` is the only place that talks to the BharatCode API. It handles configuration, caching, budgets, retries, and cache invalidation. `engine/prompts.js` is its counterpart: pure functions that build the three prompt templates the pipeline sends. Together they sit at step 3 of the flow you traced in `engine/index.js` — after ingest and rank (lesson 5), before manifest and render (lessons 4 and 8).

### Configuration comes from the environment

`configFromEnv()` at `engine/llm.js:19` reads `BHARATCODE_API_KEY`, `BHARATCODE_BASE_URL`, `BHARATCODE_MODEL`, and `BHARATCODE_REASONING_EFFORT`, falling back to `DEFAULT_BASE_URL` and `DEFAULT_MODEL` at `engine/llm.js:16-17`. Note the `.replace(/\/+$/, '')` on the base URL — trailing slashes are stripped so request paths concatenate cleanly. `missingConfig()` (`engine/llm.js:29`) reports what's absent, and the comment at `engine/llm.js:13-14` states the invariant that the API key is never written to the manifest, cache, or `LEARN.md`.

### The client's guard rails

`BharatCodeClient` (`engine/llm.js:43`) takes a `budget` (default 250,000 tokens), a `cacheDir`, `useCache`, `timeoutMs`, and an injectable `fetchImpl` for testability. When the budget is exhausted the client throws `BudgetError` (`engine/llm.js:5`) instead of silently over-spending. Responses are cached under `cacheDir/responses` and `clearCache()` (`engine/llm.js:156`) wipes them with `force: true`, which is what makes offline regeneration cheap. `extractText()` (`engine/llm.js:144`) digs `data.choices[0]` out of the response shape.

### The three prompts

`engine/prompts.js` exports a shared `SYSTEM` prompt (`engine/prompts.js:6`) plus three builders, each returning `{ system, user, maxTokens }`:

- `outlinePrompt()` (`engine/prompts.js:11`) — repo tree, ranked files, docs, entry slices in; a JSON `{summary, lessons}` out, capped at 3000 tokens. It constrains lessons to the ranked list, which is why ranking (lesson 5) matters.
- `lessonPrompt()` (`engine/prompts.js:41`) — the course outline plus line-numbered slices in; 250–450 words of Markdown out, max 2000 tokens, ending in a "**Watch out:**" line.
- `quizPrompt()` (`engine/prompts.js:65`) — lesson body plus slices in; two JSON multiple-choice questions out, max 1200 tokens.

`retrySuffix()` (`engine/prompts.js:84`) appends rejection feedback when a response violates the JSON contract.

Read `engine/prompts.js` first to see what data each stage demands, then `engine/llm.js` for how those requests are paid for and cached.

**Watch out:** reasoning tokens count against `max_tokens` (comment at `engine/llm.js:24`), so raising `BHARATCODE_REASONING_EFFORT` silently eats into the lesson/quiz budgets — and every prompt says "JSON only," so a prose answer is rejected and re-sent with `retrySuffix()`.

## 7. Synthesis paths, model vs offline

**Files:** [`engine/synth.js`](engine/synth.js) · [`engine/offline.js`](engine/offline.js)

### Two ways to fill a lesson

`engine/synth.js` and `engine/offline.js` are the two ends of a spectrum: paid model calls versus zero-token heuristics. Both produce the same artifacts — an outline, lesson bodies, and quizzes — so the rest of the pipeline (manifest, `LEARN.md`) never needs to know which one ran.

### The model path

`engine/synth.js` is the LLM-driven path. Its header comment states the contract: outline → lessons (run in parallel) → quizzes, with every response validated and retried once before degrading. That retry loop lives in `callValidated()` at `engine/synth.js:15`, which appends `retrySuffix(error)` to the prompt on the second attempt and throws if validation fails again.

Validation itself is exported and layered: `validateOutline()` at `engine/synth.js:27` requires valid JSON via `parseJSONLoose` and a `summary` of at least 40 characters; `validateBody()` at `engine/synth.js:56` cleans the text through `cleanBody()` (line 46) against the lesson title; `validateQuiz()` at `engine/synth.js:65` checks quiz JSON. The entry point `synthesizeWithModel()` (line 75) takes `repoId`, `ing`, `ranked`, `teaching`, `client`, and knobs like `maxLessons`, `concurrency = 4`, and `log` — the same ingest/rank/select outputs you met in lesson 5.

### The offline path

`engine/offline.js` makes no model calls at all. Its comment names three uses: the `--offline` flag, an outline fallback when the model's outline is unusable, and the degraded body after a failed synthesis. So it is both a standalone mode and a safety net inside `engine/synth.js` (imported at line 9 as `offlineLessonBody` and `offlineOutline`).

Reading order: `offlineOutline()` at `engine/offline.js:74` groups files and chunks them into up to `maxLessons` lessons; `offlineLessonBody()` (line 131) and `offlineQuiz()` (line 156) fill them in; `offlineCourse()` (line 207) composes all three over `ing`, `ranked`, and `teaching`. ## 8. Interactive learning TUI

**Files:** [`cli/tui.js`](cli/tui.js)

### What `cli/tui.js` does

This single file is the entire interactive experience. It takes the already-rendered `course` object (the same one the engine pipeline produced in earlier lessons) and turns it into a keyboard-driven session with four screens: **list**, **lesson**, **quiz**, and **done**. The screen dispatch is a one-liner at `cli/tui.js:198` where `draw()` looks up the current screen name in `st.screen` and calls the matching renderer.

### How it connects to the rest of the course

The TUI is the last consumer of the course manifest. It imports only two things from the engine layer:

- `progressPath` from `engine/manifest.js` (line 8) — gives the canonical path to `.curriculo/progress.json`.
- `readJSON` / `writeJSON` from `engine/util.js` (line 9) — the same helpers the engine uses everywhere.

This means the TUI never re-parses source files or re-ranks anything; it works entirely from the in-memory `course` object passed in by `cli/index.js` and the on-disk progress file.

### Reading order within the file

1. **`runTUI({ course, root })`** at line 75 — the public entry point. It returns a `Promise` that resolves when the user quits, which is how `cli/index.js` can `await` the session and then continue (e.g., to print a summary).
2. **`loadProgress`** at line 59 — reads `.curriculo/progress.json` and merges it with the lesson list so previously-completed lessons show a checkmark.
3. **The four `draw*` functions** (lines 112, 140, 152, 178) — each returns an array of styled strings. `header()` at line 97 computes the "3/7 done" counter; `footer()` at line 105 prints the key hints.
4. **`onKey`** at line 250 — the single keypress handler that routes arrows, `Enter`, `o` (open file), `q` (quit), etc. based on the current screen.
5. **`enter()` / `leave()`** at lines 312 and 319 — toggle the terminal's alternate screen buffer (`\x1b[?1049h` / `\x1b[?1049l`) so the TUI doesn't pollute the user's scrollback.

### Progress and file-opening

`finishLesson()` at line 225 writes the updated progress back to disk via `writeJSON`, making the session resumable across terminal restarts. `openFile(rel)` at line 204 resolves the relative path against `root` and spawns the user's `$VISUAL` or `$EDITOR` (determined by `editorCommand()` at line 65), letting a learner jump straight to the source file a lesson references.

### Non-interactive fallback

`printCourse(course)` at line 343 is a simple `console.log` loop for when the user passes a `--no-tui` flag or the terminal isn't a TTY. It's the same data, just without the state machine.

**Watch out:** The TUI uses `readline.emitKeypressEvents` (line 313) to get raw keypresses, but it never calls `readline.setRawMode(true)` explicitly in the visible excerpt — the raw-mode setup is likely handled inside `enter()` or by the readline interface itself. If you add a new key binding, test it in a real terminal; some editors (e.g., VS Code's integrated terminal) swallow `Ctrl+C` before it reaches the handler.
